## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | **Мартинсон Диана Вадимовна** |
| Вариант (запрос) | **Вариант 2 — Q10 «Returned Item Reporting»** |
| Масштаб `sfN` | `sf1` |
| Почему выбрал такой масштаб | `sf1` позволяет проверить объединение четырёх таблиц и выполнить все этапы медальона локально на Windows с Docker. В самом большом источнике `lineitem` — 6 001 215 строк, что достаточно для эксперимента с хранением и кодеками без перехода на существенно более тяжёлые `sf10` и `sf100`. Во всех слоях и в тестах сжатия используется один масштаб `sf1`. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (`quay.io/minio/minio:latest`) | S3-совместимое объектное хранилище, в котором находятся физические файлы Iceberg/Parquet | Позволяет хранить данные отдельно от SQL-движка и предоставлять к ним S3-совместимый доступ как Trino, так и Spark. В фактически работающем контейнере использован образ MinIO, а не Silo. |
| PostgreSQL (`postgres:17`) | Хранение служебных метаданных Lakekeeper | Обеспечивает работу REST-каталога; большие аналитические таблицы хранятся в MinIO, а не в PostgreSQL. |
| Lakekeeper (`quay.io/lakekeeper/catalog:latest-main`) | Iceberg REST Catalog | Централизованно предоставляет метаданные таблиц и информацию о снапшотах двум вычислительным движкам. |
| Trino (`trinodb/trino:476`) | SQL-движок для генерации TPC-H, преобразования Bronze → Silver → Gold, выполнения Q10 и замеров | Позволяет работать с TPC-H и Iceberg одним SQL; чтение и запись данных выполняются через Lakekeeper и MinIO. |
| Apache Spark (`apache/spark:3.5.3`) | Дополнительный движок для проверки чтения Bronze | Проверяет, что те же таблицы Iceberg доступны другому движку без повторной загрузки данных |


### Скрипты, которыми поднимал стек

В ходе данной практической использовались четыре основных контейнера:

```powershell
# Проверка контейнеров и готовности PostgreSQL/Lakekeeper.
docker ps -a
docker ps
docker exec lakehouse-pg pg_isready
curl.exe http://localhost:8181/health

# Проверка SQL-движка и каталогов.
docker exec trino trino --execute "SHOW CATALOGS"
docker exec trino trino --execute "SHOW SCHEMAS FROM lakekeeper"
docker exec trino trino --execute "SHOW SCHEMAS FROM tpch"

# Создание рабочих схем в уже работающем каталоге Lakekeeper.
docker exec trino trino --execute "CREATE SCHEMA IF NOT EXISTS lakekeeper.bronze"
docker exec trino trino --execute "CREATE SCHEMA IF NOT EXISTS lakekeeper.silver"
docker exec trino trino --execute "CREATE SCHEMA IF NOT EXISTS lakekeeper.gold"
```

**Команда фактического запуска дополнительного инструмента** (подготовленные конфигурация и JAR-файлы находятся в `spark/`):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\spark\run-spark.ps1
```

Содержимое `spark/run-spark.ps1`:

```powershell
docker run -it --rm `
  -v "${PWD}/spark/conf:/opt/spark/conf" `
  -v "${PWD}/spark/jars:/opt/spark/iceberg-jars" `
  apache/spark:3.5.3 /opt/spark/bin/spark-sql
```

Файлы конфигурации основных сервисов и команды их первоначального развёртывания находятся в проекте (`setup-windows.ps1`, `catalog/`, `create-warehouse.json`). Действующий контейнер Trino использует порт **8081** на компьютере.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `custkey`, `name`, `acctbal`, `nationkey`, `address`, `phone`, `comment` | `custkey` связывает клиента с заказами; `nationkey` связывает клиента со страной; прочие поля выводятся и включаются в группировку. |
| `orders` | `orderkey`, `custkey`, `orderdate` | Соединение по `custkey` и `orderkey`; отбор заказов по условию `orderdate >= DATE '1993-10-01' AND orderdate < DATE '1994-01-01'`. |
| `lineitem` | `orderkey`, `extendedprice`, `discount`, `returnflag` | Соединение по `orderkey`, отбор `returnflag = 'R'`, расчёт выручки `sum(extendedprice * (1 - discount))`. |
| `nation` | `nationkey`, `name` | Соединение со справочником стран по `nationkey`; `name` выводится под именем `nation`. |

Q10 формирует **20 клиентов с наибольшей выручкой от возвращённых позиций в IV квартале 1993 года**, с сортировкой `revenue DESC` и `LIMIT 20`. Проверочный исходный SQL содержится в `sql/05_validation.sql`. Результат Gold и исходного Q10 совпал по составу и порядку 20 клиентов; для денежных значений наблюдались небольшие различия в последних разрядах чисел с плавающей точкой (например, `734235.2455000001` и `734235.2455`), поэтому посимвольное совпадение всех значений не заявляется.

## 4. Медальон — решения по каждому слою

Количество строк подтверждено результатами `CREATE TABLE AS SELECT` и/или `SELECT count(*)`. Размеры получены запросами `sum(file_size_in_bytes) / 1048576.0` из системных таблиц Iceberg `"<имя>$files"`. Значения в МБ округлены выводом SQL; `0.0` у маленьких таблиц означает округление размера файлов. Партиционирование явно не задавалось.

## 5. Тесты производительности

Сравнение проводилось на **одинаковых полных наборах колонок и строк Bronze** в формате PARQUET: исходные таблицы с ZSTD и их копии с GZIP. Оба SQL-запроса реализуют один Q10 и отличаются лишь именами исходных таблиц. Для каждой комбинации выполнено **три запуска**. Измерения проводились PowerShell-командой `Measure-Command` вокруг передачи SQL в `docker exec -i trino trino`; таким образом, результат включает запуск клиента Trino и обмен результатами.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---:|---|
| GZIP | **6,487 сек. в среднем** (запуски: 7,668; 5,927; 5,867 сек.) | **184,9** | В данном тесте GZIP занял примерно на 5,0 МБ меньше и показал среднее время примерно на 0,148 сек. меньше. Для полученного набора измерений оказался немного выгоднее по обоим показателям. |
| ZSTD | **6,635 сек. в среднем** (запуски: 7,999; 5,992; 5,913 сек.) | **189,9** | ZSTD использован как рабочий вариант хранения медальона. Он показал близкое время Q10, но в этих измерениях занял немного больше места. |

**Размеры отдельных таблиц (МБ):** ZSTD — `customer 7,8`, `orders 34,9`, `lineitem 147,2`, `nation 0,0`; GZIP — `gzip_customer 7,7`, `gzip_orders 33,5`, `gzip_lineitem 143,7`, `gzip_nation 0,0`. Итоговая экономия GZIP по округлённым значениям — около **2,6%**. Разница по среднему времени — около **2,2%**; она невелика и может зависеть от кэша, прогрева, нагрузки компьютера и накладных расходов клиента. 

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse сочетает объектное хранение файлов (MinIO) с табличной моделью и SQL-доступом через Iceberg и Lakekeeper. Вычисления и хранение разделены: Trino создаёт и запрашивает таблицы, а Spark читает те же Bronze-данные без их копирования в отдельную БД. При большом объёме данных это даёт гибкость работы разными движками и возможность хранить сжатые колоночные файлы. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Выполнено `ALTER TABLE lakekeeper.silver.returned_items ADD COLUMN note varchar;`. Команда завершилась успешно, `SHOW COLUMNS` показал **12 столбцов** вместо 11. Проверка `SELECT count(*) AS total_rows, count_if(note IS NULL) AS null_rows ...` вернула **114705 / 114705**: все старые строки сохранились, новая колонка содержала `NULL`. Затем выполнено `ALTER TABLE ... DROP COLUMN note;`, после чего `SHOW COLUMNS` снова показал исходные **11 столбцов**. Пересоздавать Silver или заново загружать её данные не потребовалось. |
| Пример скрипта восстановления данных из снапшота (time travel) | Через системную таблицу `"returned_items$snapshots"` найден снапшот с ID **`1790828416848786939`**, временем **`2026-10-11 11:45:16.233 UTC`** и операцией `append`. Чтение `FOR VERSION AS OF 1790828416848786939` вернуло **114 705 строк**. Затем создана отдельная таблица `lakekeeper.silver.returned_items_restored` из этого снапшота; проверка `count(*)` также вернула **114 705 строк**. Исходная таблица не откатывалась и не заменялась. Скрипт приведён ниже. |

```sql
-- Просмотр версий
SELECT committed_at, snapshot_id, operation
FROM lakekeeper.silver."returned_items$snapshots"
ORDER BY committed_at DESC;

-- Чтение конкретной версии; результат: 114705 строк.
SELECT count(*)
FROM lakekeeper.silver.returned_items
FOR VERSION AS OF 1790828416848786939;

-- Восстановление в отдельную таблицу из снапшота
CREATE TABLE lakekeeper.silver.returned_items_restored
WITH (format = 'PARQUET') AS
SELECT *
FROM lakekeeper.silver.returned_items
FOR VERSION AS OF 1790828416848786939;

-- Фактический результат проверки: 114705 строк.
SELECT count(*) FROM lakekeeper.silver.returned_items_restored;
```

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark 3.5.3 (SQL-движок) | Spark указан среди допустимых инструментов. Для этой работы он удобен тем, что поддерживает Iceberg и может проверить таблицы Bronze, уже созданные через Trino: отдельный BI-дашборд не требуется, а взаимодействие с данными легко подтвердить SQL-запросами. |

**Скрипты развёртывания**:

```powershell
.\spark\download-jars.ps1

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\spark\run-spark.ps1
```

Скрипт `spark/run-spark.ps1` монтирует `spark/conf` и `spark/jars` в Docker-контейнер `apache/spark:3.5.3` и запускает `/opt/spark/bin/spark-sql`. Для Iceberg использованы `iceberg-spark-runtime-3.5_2.12-1.7.1.jar` (42 797 968 байт) и `iceberg-aws-bundle-1.7.1.jar` (49 573 793 байт). В `spark/conf/spark-defaults.conf` задан каталог `lakekeeper` через REST API `http://host.docker.internal:8181/catalog` и S3-хранилище `http://host.docker.internal:9000`.

**Свои действия в консоли Spark и фактические результаты:**

```sql
SHOW TABLES IN lakekeeper.bronze;

-- Время 10.166 с; 8 строк в выводе.

SELECT count(*) FROM lakekeeper.bronze.customer;
-- Результат: 150000; время 16.223 с.

SELECT nationkey, name FROM lakekeeper.bronze.nation LIMIT 10;
-- Результат: 10 стран; время 7.131 с.
```

Spark показал десять записей: `0 ALGERIA`, `1 ARGENTINA`, `2 BRAZIL`, `3 CANADA`, `4 EGYPT`, `5 ETHIOPIA`, `6 FRANCE`, `7 GERMANY`, `8 INDIA`, `9 INDONESIA`. **Подключение к Bronze и чтение данных подтверждены:** таблицу `customer`, загруженную Trino, Spark прочитал с тем же количеством строк (**150 000**).

## 7. Выводы

В практической работе реализованы связанные слои Bronze, Silver и Gold на данных `tpch.sf1`: из четырёх исходных таблиц получена витрина двадцати клиентов по выручке от возвращённых товаров. Формат Parquet в MinIO и каталог Iceberg Lakekeeper позволили разделить физическое хранение, метаданные и вычисления, а Spark подтвердил чтение тех же таблиц другим SQL-движком. При сравнении одинаковых наборов Bronze в этом локальном эксперименте GZIP занял **184,9 МБ** против **189,9 МБ** у ZSTD и показал немного меньшее среднее время Q10 (**6,487** против **6,635 сек.**), хотя различие во времени невелико. Изменение схемы Silver не привело к потере строк, а чтение и восстановление данных из снапшота подтвердили возможности Iceberg. Для данного объёма `sf1` отказ от партиционирования позволил сохранить простую структуру медальона без дополнительных разделов данных.
